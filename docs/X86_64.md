# VesperOS 4 "Nebula" on x86_64

VesperOS now builds as a **64-bit (x86_64) kernel**. The proven 32-bit kernel is kept and built into the same ISO, so
the GRUB menu offers both:

    VesperOS 4 Nebula (0.10) - i686 32-bit (proven, default)
    VesperOS 4 Nebula (0.10) - x86_64 64-bit (testing)

The 32-bit kernel is the default until the 64-bit one is confirmed good on real hardware. The menu waits 10 seconds. Everything else (shell, drivers, hespernetd, packages) is the same source code compiled
for both targets.

## Build

    make check      # which tools are missing
    make iso        # builds both kernels + vesperos4.iso      (needs nasm only for the i686 boot stub)
    make verify     # mechanical checks of the built images    (python3; run it before you boot anything new)
    make test       # network tests + arch tests + image verification

`make x64` / `make i686` build one kernel. Toolchain is auto-detected (gcc/ld or clang/ld.lld); override with
`make CC=clang LD=ld.lld`. The x86_64 boot code is GNU-syntax `.S` built by `$(CC)`, so it needs no nasm.

## Why 64-bit

* **BARs above 4 GiB.** A 32-bit kernel cannot reach a PCI BAR firmware placed above 4 GiB (the RTL8168 only worked
  because it also has an I/O-port window). `mmio_map()` now maps such ranges on demand (uncached, 2 MiB pages).
* **The framebuffer address was being truncated to 32 bits** (a latent bug even on i686). It now goes through `mmio_map()`.
* Modern software is 64-bit, and long mode needs paging, IDT and GDT, which the roadmap needs anyway.

## Boot flow (arch/x86_64/boot.S)

GRUB loads the ELF64 image via multiboot2 and enters `_start` in 32-bit protected mode (`eax` = magic, `ebx` = info block).
The stub is a straight line with no loops, using prebuilt page tables:

    cpuid check -> CR4.PAE -> CR3 = boot_pml4 -> EFER.LME -> lgdt -> CR0.PG -> far jump -> 64-bit code -> kernel_main(magic, info)

Page tables (`arch/x86_64/boot_tables.S`, generated by `tools/gen_boot_tables.py`) identity-map **0..4 GiB** with
2 MiB pages, so `virtual == physical` exactly as before: every driver address, DMA buffer and BAR below 4 GiB is
numerically unchanged. The kernel stays at 1 MiB (a higher-half layout is deliberately left for the memory-manager step).

`kernel_main` first calls `arch_early_init()`, which loads a GDT + TSS + IDT (arch/x86_64/traps.c). From then on a CPU
fault prints a register dump instead of silently rebooting. Hardware interrupts stay disabled, as before.

## Debugging aids (use them when something goes wrong)

| What you see | Meaning |
|---|---|
| GRUB prints an error before the kernel starts | the image was rejected (header/ELF problem): run `make verify` |
| black screen, machine reboots in a loop | triple fault inside the boot stub, before `kernel_main` |
| red **KERNEL EXCEPTION** screen with registers | the kernel ran and faulted: photograph it. `RIP_offset_in_image` + `nm -n vesperos4-x86_64.bin` names the function |
| normal boot, line "x86_64 long mode ..." | success |

* **POST codes** (port 0x80, visible on a motherboard debug display): `10` stub entered, `11` CPU supports long mode,
  `12` paging enabled, `13` in 64-bit code, `EE` CPU lacks long mode.
* **Debug console** (port 0xE9 and COM1): boot stages `1 2 3 4`, `[x64] ...` messages and every crash dump.
  Under QEMU: `-debugcon file:qemu-debug.log` (the `make run` targets do this).
* `crashtest yes` in the shell deliberately executes `ud2` to prove the handler works on your machine.

## What is verified, and what is not

Verified without booting (`make test`, `make verify`):
* Both kernels compile warning-free; the compiler's pointer-truncation checks are clean for x86_64.
* Image layout: ELF64, entry < 4 GiB, loaded at >= 1 MiB, exactly four segments, multiboot2 header inside GRUB's 32 KiB window
  with a correct checksum, entry is `_start`.
* Page tables read back out of the ELF: PML4/PDPT/PD chain and all 2048 entries == identity map.
* Mode-switch instruction order (PAE, CR3, LME, lgdt, PG, far jump) read from the raw opcode bytes; GDT descriptors correct.
* No SSE/x87 instruction anywhere in the image (SSE is not enabled; the first one would fault).
* IDT gate and TSS descriptor encodings, trap-frame layout vs the assembly stubs, crash-dump text (fits 80 columns),
  `mmio_map()` page-table edits - unit-tested on the host under ASan/UBSan.

**Not verified:** actually executing the 64-bit boot path. That needs a VM or real hardware; the first boot on your
machine is the real test. The i686 entry exists for exactly that reason.

## First real-hardware report and what changed because of it

The first boot of the 64-bit kernel on real hardware (AMD board, xHCI keyboard, RTL8168) reached the shell, so the boot
stub, page tables and screen output are proven. But the USB keyboard did not work and the NIC reported no address. That
points at device behaviour that differs between the two builds, not at the boot path. Changes made in response:

* **First 2 MiB now uses 4 KiB pages** (boot_pt0). The old 2 MiB page spanned the legacy VGA/ROM hole, which the fixed MTRRs
  type differently from RAM: undefined behaviour per Intel SDM Vol.3 11.11.8. The hole is now uncached, RAM write-back.
* **xHCI TRBs are `volatile`**, with a compiler read barrier after an event is seen, and **every port I/O access is a compiler
  memory barrier** (GCC may otherwise cache DMA-written memory across polling loops).
* **Self-diagnosis at boot**: if no USB HID device enumerates, the boot screen prints the controller summary and the exact
  enumeration step that failed; if a NIC has no address it prints a compact register/ring dump. Both are readable with a
  photo even when the keyboard does not work.
* hespernetd waits up to 6.5 s for link (was 3.5 s, borderline for gigabit autonegotiation) and prints a one-line
  "[ net ] eth0 is now up: ..." notice when a lease arrives after boot.

## Second real-hardware report (UEFI vs BIOS)

* **DHCP now works on x86_64** (longer link wait). **The 32-bit kernel is unaffected.**
* **UEFI x86_64: keyboard enumerated but no keys; BIOS/CSM x86_64: keys work.** BIOS mode normally offers USB "legacy
  emulation" (the keyboard appears as PS/2), so working on BIOS does not prove the xHCI driver is right; under UEFI there
  is no such crutch. The xHCI spec requires contexts not to cross a 4 KiB page and rings not to cross a 64 KiB boundary;
  where the compiler placed the old unaligned arrays differs between 32-bit and 64-bit (and gcc and clang) builds, and a
  controller that loses events after enumeration would look exactly like this. Every xHCI DMA structure is now 4 KiB-page
  aligned, with compile-time size checks, and `make verify` checks the real addresses in the finished image
  (so it also validates your clang/lld build). Not yet confirmed on hardware.
* **The screen "wipe" on UEFI** (visible sweep on `clear` and when output scrolls) was the framebuffer renderer reading
  video memory to scroll and writing one pixel per call to clear. See `RELEASE.md`; tested pixel-for-pixel against the
  old renderer (`make test-vga`).

## Known limits

* Kernel is identity-mapped and runs in ring 0 only; no per-process address spaces yet.
* MMIO above 4 GiB is mapped uncached (right for registers, slow for a framebuffer). Write-combining is future work.
* Still polled I/O, single CPU, 64 KiB heap.
* `mmio_map()` has room for 8 distinct GiB regions above 4 GiB and 512 GiB of address space.
